# 角色动画 Final Project 实验报告

## 一、方案选择与总体目标

本项目采用方案二，基于 Motion Matching 实现可交互控制。

与 lab2 中手工搭建 Motion Graph 的做法不同，Motion Matching 无需事先切割动画，也不必人为规定动作之间的转移关系。其基本流程是：每一帧将用户输入所期望的未来一小段轨迹（位置、朝向、速度、角速度）抽象为一组查询特征，在动作数据库中检索特征最接近的候选帧，再通过惯性化平滑过渡。当前动作到目标动作之间的过渡由算法自动完成，无需人工介入；由于候选帧均来自真实动捕数据，生成的动作也能保持自然。

方案二的基础要求包括四项：至少支持走、跑、转向及三者之间的切换；走、跑、转向能及时响应键盘与摇杆；转向时具有明显的转身动作，整体无明显跳变；并提供实现说明。

上述要求本实现均已满足，此外还支持了站立（idle），转向也区分为左右两个方向。全部代码位于 `answer_project.py`，评测入口 `task1_project.py` 的接口未作改动，可直接运行。

## 二、数据准备

在 `CharacterController.__init__` 中，我将 `motion_material` 下的短动作与长动作纳入数据库，共 9 个数据源：

| 名称 | 文件 | 类别 (kind) |
|------|------|------|
| idle | idle.bvh | idle |
| walk | walk.bvh | walk |
| run | run.bvh | run |
| long_walk | long_motion/long_walk.bvh | walk |
| long_walk_mirror | long_motion/long_walk_mirror.bvh | walk |
| long_run | long_motion/long_run.bvh | run |
| long_run_mirror | long_motion/long_run_mirror.bvh | run |
| turn_left | turn_left.bvh | turn_left |
| turn_right | turn_right.bvh | turn_right |

匹配质量主要依赖长 motion。`long_walk`、`long_run` 及其镜像片段连续且相位丰富，可提供大量候选帧；短 motion 则用于补足库中缺少的动作类型，如站立与转向。相比 lab2 仅有的 5 个手工修整过的片段，这里在数量与种类上都更充分。

数据仅依赖 `numpy`、`scipy` 以及作业自带的 `bvh_loader` 和 `physics_warpper`，未引入其他库，符合评测要求。

## 三、代码结构与文件说明

全部逻辑集中在 `answer_project.py`，主要由四个类构成。

`MotionSource` 封装单个 BVH 动作，负责载入动作、将根关节坐标系归一化到统一朝向，并预先计算根位置、根朝向（yaw）、根速度与加速度、角速度与角加速度等运动特征。对可循环的动作（idle、walk、run），它会用 `build_loop_motion` 完成首尾拼接，并记录一个循环周期内根的位移与转角增量。

`MotionDatabase` 将所有 `MotionSource` 的候选帧展开为一张扁平的特征表。每个候选帧保存的是以当前帧为原点、当前朝向为参考系下，未来 6 个时间点（偏移 0/20/40/60/80/100 帧）的局部轨迹特征。这些特征在初始化时一次性向量化算好，运行时只需矩阵广播即可完成全库打分。

`CharacterController` 是控制器主体，也是整个 Motion Matching 的核心。它在每帧构造查询特征、检索最佳候选、判断是否切换、执行惯性化过渡，并输出当前帧的骨骼位姿。

`PDController` 为物理控制的占位类。本项目走 kinematics 路线（`simu_flag=0`），其中几个施力接口均为空实现，不参与仿真。

运行方式与原始作业一致：

```bash
python task1_project.py
```

W/A/S/D 或方向键控制移动方向，空格切换跑步相关的 gait，鼠标控制相机；若检测到手柄，则由左摇杆移动、右摇杆控制视角。

## 四、核心算法实现细节

### 4.1 运动特征的定义

Motion Matching 的关键在于用什么特征描述一个动作瞬间。本实现采用轨迹特征与速度特征的组合，对每个候选帧记录未来 6 个采样点（帧偏移 `OFFSETS = [0, 20, 40, 60, 80, 100]`）的以下几项：

- 局部根位置偏移 `pos_offsets`，即未来各点相对当前帧根位置的位移，投影到 XZ 平面后旋转至当前朝向的局部坐标系；
- 局部根速度 `vel_local` 与局部根加速度 `acc_local`；
- 相对朝向偏移 `yaw_offsets`，即未来各点 yaw 相对当前 yaw 的差值，并做 `wrap` 处理；
- 绕 Y 轴的角速度 `avel_y` 与角加速度 `aacc_y`。

所有特征都换算到当前帧的局部坐标系下，使匹配与角色所处的世界位置、世界朝向无关，只关注接下来这段路如何走、如何转。这也是 `_rotate_xz` 用 `-base_yaw` 将世界向量旋回局部系的原因。

速度、加速度、角速度均由有限差分求得（`_motion_root_velocity`、`_motion_root_acceleration`、`_motion_yaw_velocity` 等），与作业提示中"速度和角速度是重要动作特征，一般通过有限差分计算"的建议一致。

### 4.2 查询特征与数据库特征的时间对齐

有一处容易被忽略但相当关键：查询轨迹的时间采样必须与数据库特征的时间采样对齐。`viewer/controller.py` 中的 `Controller` 用阻尼弹簧（`simulation_positions_update`、`simulation_rotations_update`）预测未来轨迹，其 `future_step = 6`、`sub_step = 20`，即每隔 20 帧预测一个点，恰好 6 个点、跨度 100 帧；数据库这一侧的 `OFFSETS` 同样取 `[0,20,40,60,80,100]`，二者一一对应。`_desired_features` 的作用便是把控制器给出的 `future_pos/rot/vel/avel` 转换为与数据库同构的局部特征，从而可以逐点相减比较。

### 4.3 匹配打分函数

打分在 `_score_candidates` 中完成，对整张数据库做一次向量化的加权平方误差：

```
score = W_POS  · ‖Δpos‖²  + W_VEL · ‖Δvel‖²  + W_SPEED · Δspeed²
      + W_FORWARD · forward_shortfall² + W_ACC · ‖Δacc‖²
      + W_YAW · Δyaw²  + W_AVEL · Δavel² + W_AACC · Δaacc²
      + 转向项 / 非转向项惩罚 + 动作类别偏置
```

各权重（`W_POS=2.2`、`W_VEL=3.2`、`W_YAW=4.8` 等）依据实际效果调定，整体使朝向和速度占主导。对可交互控制而言，转向是否到位、速度是否匹配是用户最直接的感受，因此这两项的分量较重。

除基本的轨迹误差外，我还加入了几组针对性项目，用于消除常见的动作瑕疵。`forward_shortfall` 是前进不足惩罚，当候选帧的前向速度明显低于期望时额外加罚，避免角色在需要快走或跑时前进乏力。转向方向项针对 `turn_left`、`turn_right` 类候选：转向方向与期望相反（`wrong_turn`）时重罚，方向一致（`matched_turn`）时给予奖励；当期望几乎不转（`quiet_turn`）时则压低转向片段的得分，防止直行时误触发转身。非转向片段的偏航惩罚则约束走、跑片段：若其自身带有较大转角（`|candidate_turn| > 0.35`），在需要转向时会被 `W_NON_TURN_YAW` 与 `W_NON_TURN_ABS_YAW` 显著惩罚，从而把转弯交由真正的转向片段完成，而非依靠走路片段硬拐。

最后再叠加一层动作类别门控。`_target_kind` 先判定当前应处于 idle、walk、run、turn 中的哪一类，不属于该类的候选帧会被加上较大偏置，必要时以 `+1000` 直接硬屏蔽，确保检索结果落在正确的动作语义上。`_target_kind` 综合期望速度大小、未来最大偏航角与手柄 gait 判断目标动作，并对进入转向与退出转向设置了不同阈值（`TURN_ENTER_YAW=0.18` 与 `TURN_EXIT_YAW=0.12`），形成迟滞，避免在临界角度反复横跳。

### 4.4 搜索时机与切换策略

若每帧都无条件跳向全局最优候选，动作会因切换过于频繁而抖动。因此 `_maybe_search` 中的切换策略较为克制。

搜索间隔方面，普通动作每 `SEARCH_INTERVAL=30` 帧搜索一次，转向时缩短至 `TURN_SEARCH_INTERVAL=12` 帧以提升响应；非循环片段临近结尾时（`near_end`）强制搜索，避免播放到头。切换判定方面，先用 `_current_score` 算出继续沿当前片段播放的代价，只有当最优候选明显更优、差值超过 `CURRENT_MARGIN=0.45` 时才考虑切换，由此抑制大量无意义的微小跳转。跨源切换更为保守，切换到不同数据源需要更大的优势裕度（`CROSS_SOURCE_MARGIN=2.5`，同类动作之间为 `SAME_KIND_SWITCH_MARGIN=4.0`）；同源近邻（帧号差小于 20）则不切换，顺势播放。转向片段进入后至少驻留 `TURN_MIN_SWITCH_FRAMES=12` 帧，保证转身动作能够完整表达，不致转到一半被打断。

这套策略的实际效果是：直行时角色在长 motion 上连续平滑地走或跑，只有当输入方向真正改变时才发生切换，切换点也尽量落在动作语义匹配的位置。

### 4.5 惯性化过渡（Inertialization）

即便切换点选得再好，两个片段在关节层面仍会存在细微差异，直接硬切会产生跳变。为此我实现了基于阻尼弹簧的惯性化过渡（`_begin_inertialization` 与 `_apply_inertialization`）。

切换发生时，先记录切换前姿态与新片段目标姿态之间的偏差（位置偏差 `inertial_pos_offset`、旋转偏差 `inertial_rot_offset`，二者均对根关节置零以免影响位移），随后在 `BLEND_FRAMES=12` 帧内，让该偏差按半衰期 `INERTIAL_HALFLIFE=0.12s` 的临界阻尼弹簧衰减至零（`_decay_spring_pos`、`_decay_spring_rot`）。也就是说，切换瞬间角色仍保持切换前的姿态，其后偏差再逐渐融入新片段。这正是作业提示所推荐的 Inertialization 思路，`smooth_utils.py` 中也给出了对应的 damped spring 参考实现。

### 4.6 坐标系对齐与循环动作处理

每个 BVH 片段有各自的起始朝向与世界位置，直接拼接会导致角色瞬移或扭头。处理方式如下。`MotionSource._normalize_root_coordinate` 在载入时先将每个片段旋转到统一的初始朝向。`_aligned_local_pose` 在输出每一帧时，借助锚点帧（`anchor_frame`）、锚点世界位置（`anchor_pos`）、锚点朝向（`anchor_yaw`）与对齐旋转（`align_rot`），把片段的局部运动贴合到角色当前的世界位姿上，保持根位置与朝向连续。对走、跑、站立这类需要在世界中持续前进的动作，根朝向直接由 `anchor_yaw + yaw_delta` 重建，以避免累计漂移。

循环片段跨越周期边界的情况由 `_wrap_current_loop` 处理。当播放超过一个循环周期时，将帧号取模回到周期内，同时把 `anchor_pos` 与 `anchor_yaw` 按该片段一个周期的位移、转角增量（`cycle_root_delta`、`cycle_yaw_delta`）向前推进，使角色能够沿长 motion 持续前行而不跳回原点。

此外，`_aligned_local_pose` 对根的竖直高度做了 `±0.08` 的限幅，避免不同片段根高差异造成上下弹跳；`sync_controller_and_character` 则将角色的实际位移反馈回控制器与相机，使摇杆轨迹、相机与角色三者保持同步。

## 五、交互响应

用户输入先经 `Controller.get_desired_state` 转换为未来 6 个采样点的期望轨迹，再送入 `CharacterController.update_state`。由于匹配特征以速度和朝向为主导，转向时搜索间隔又缩短至 12 帧，角色对方向变化的反应较为迅速。

走与跑的切换由期望速度大小和手柄 gait 共同决定，速度超过 `RUN_SPEED=1.65` 或 gait 为 1 时判为跑，再由类别门控保证检索落到对应片段上。转向时，只要未来轨迹的偏航角超过进入阈值，`_target_kind` 便判定为 `turn_left` 或 `turn_right`，检索会被强制引向真正的转身片段，因而转向时可见清晰的转身动作，而非原地打滑旋转。速度低于 `STOP_SPEED=0.12` 且几乎不转向时切回 idle，角色自然收步站定。

## 六、效果验证

从实际渲染运行的情况看，本实现满足方案二的全部基础要求：支持走、跑、转向与停止，键盘与摇杆控制响应及时，转向具有明显的转身动作，切换处经惯性化过渡后也无明显跳变。直行时角色沿长 motion 连续行走或奔跑；给出方向输入后，角色能在较短时间内转向到位，转向过程可见清晰的转身动作而非原地打滑；松开输入并减速至阈值以下时自然收步站定。

## 七、主要可调参数

为便于复现与调参，关键参数集中在 `CharacterController` 的类属性中，含义如下：

| 参数 | 值 | 含义 |
|------|----|------|
| `SEARCH_INTERVAL` / `TURN_SEARCH_INTERVAL` | 30 / 12 | 普通 / 转向场景的搜索周期（帧） |

## 八、总结

本项目按 Motion Matching 的思路，在纯 kinematics 路线下实现了一个响应及时、切换平滑的可交互角色控制器。相较 lab2 手工搭建 Motion Graph，它不再依赖人工连接动作，而是通过统一的局部特征表示、全库向量化检索与惯性化过渡，自动从真实动捕数据中找出最合理的续接方式。

工程上花费精力最多的有三处：一是让查询轨迹与数据库特征在时间采样上对齐；二是处理跨片段的坐标系对齐与循环续接；三是借助多层门控与裕度策略抑制无意义的频繁切换。最终角色能够自然地完成走、跑、转向与停止，并及时响应用户输入。

提交文件方面，核心实现为 `answer_project.py`，直接以原始 `task1_project.py` 运行即可，接口未作改动。所用动作数据均来自作业自带的 `motion_material`，未引入额外数据集，也未使用第三方库。
